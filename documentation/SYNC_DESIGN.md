# Working while sync runs

## Sync audit for 0.19.18

Sync services track stable item IDs and revisions, then reconcile changes against a known state. OneDrive uses push notifications in its Windows client and exposes a paged delta feed with deletion records and a full rescan when a checkpoint expires. Google Drive provides a paged change log, notification hints, and binary file revisions. Zotero uses version-conditional writes and compares current edits against the previous synced copy so it can merge independent fields. Its desktop app syncs library data separately from attachment files. [OneDrive sync](https://learn.microsoft.com/en-us/sharepoint/sync-process) · [Graph delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta?view=graph-rest-1.0) · [Google Drive changes](https://developers.google.com/workspace/drive/api/guides/manage-changes) · [Google Drive revisions](https://developers.google.com/workspace/drive/api/guides/change-overview) · [Zotero API syncing](https://www.zotero.org/support/dev/web_api/v3/syncing) · [Zotero desktop syncing](https://www.zotero.org/support/sync)

reMarkable documents automatic Wi-Fi sync between its own devices and apps. Its OneDrive, Google Drive, and Dropbox integrations copy documents in and export copies out. The plugin uses an unofficial cloud interface for stable document IDs, raw annotation layers, and root generation checks. The observed root generation protects concurrent writes. The root hash and each document hash identify snapshots, so a running helper now fetches document metadata only for new or changed revisions. It reads the full root index when the root hash changes and adopts a new snapshot only after successfully reading it. A helper restart rebuilds the in-memory catalog, and a new pairing starts a new session and catalog. [reMarkable file transfer](https://support.remarkable.com/articles/Knowledge/importing-and-exporting-files) · [reMarkable integrations](https://support.remarkable.com/articles/Knowledge/Integrations) · [rMAPI reference implementation](https://github.com/ddvk/rmapi/blob/master/api/sync15/tree.go)

| Area reviewed | Finding and behavior |
| --- | --- |
| Discovery and identity | Zotero’s local API and reMarkable’s root index supply stable keys. The plugin scopes writes to the selected pair, stages originals by SHA-256, and asks for review when paper identity or a destination is ambiguous. The cloud index parser now checks for repeated IDs in one pass. |
| Folder changes | A conflicting rename or move on both devices used to exit the bridge before document work. The affected folder pair and its descendants now pause while other folders sync. A fresh pass clears a pending conflict when the live names or locations converge. Duplicate unlinked sibling names still require distinct names before pairing can proceed. |
| Paper moves and names | The bridge now compares names and destinations independently. A rename on one side and a move on the other can be combined. The worker saves the intended Zotero membership and attachment updates before applying them, resumes a partial change, and checks for intervening edits before continuing. |
| PDF upload and publication | A retry of an uncommitted upload now verifies the live Zotero PDF against the approved original. Stable upload IDs still recover a lost response after a committed upload. Tablet annotations are rendered against the verified original. Zotero’s own attachment sync owns account uploads, and existing native annotations and publication checks govern whether a view can be updated safely. |
| Deletions and tags | Confirmed Trash operations require explicit decisions and scope checks. The worker treats an absent paper as unavailable. Tag edits use saved baselines, durable local choices, and stable page IDs. Zotero Notifier events keep local review and tag evidence fresh. |
| Zotero workflow | The reMarkable toolbar button opens Sync Conflicts when a folder decision, conflict, or sync warning is waiting. Its tooltip shows when a completed check has work for the user. The plugin uses Zotero’s local API, reader, collection, and attachment operations alongside its own scheduler. [Zotero 10 developer documentation](https://www.zotero.org/support/dev/zotero_10_for_developers) · [Zotero local writes](https://www.zotero.org/support/dev/web_api/v3/write_requests) |

The existing Python adapter and SQLite review store fit the bundled Windows build. The original AGPL-3.0 rMAPI and MIT-licensed rMapy are archived. The active AGPL-3.0 rMAPI fork offers a Windows binary and is useful as a reference for sorted schema-4 writes and hash-based catalog refresh. Its Windows and Paper Pro reports also show how upstream changes can affect unofficial clients. Switching to its Go CLI would require additional packaging and integration with the plugin’s annotation, tag, and recovery paths. The audit retains the existing adapter, reuses its content-addressed cache and the native Zotero attachment API, and adds no dependency. The tests cover Zotero 10.0.x integration and simulated reMarkable cloud revisions. Live device firmware compatibility requires a physical round trip. [Original rMAPI](https://github.com/juruen/rmapi) · [rMapy](https://github.com/subutux/rmapy) · [Active rMAPI fork](https://github.com/ddvk/rmapi) · [Windows schema report and fix](https://github.com/ddvk/rmapi/issues/76)

The first cloud catalog still reads account-wide metadata to resolve ancestry, and each Zotero profile keeps its own bridge ledger. Two Zotero computers can share library records through Zotero sync, while their plugin mappings and pending decisions remain local. The audit found no documented reMarkable change subscription that this Windows plugin could use. An account-wide delta feed, shared plugin mappings, and scoped recovery for duplicate folder names require further design and testing.

## Zotero workspace and queues

Duplicate-merge recovery uses Zotero’s native replacement relations for references and attachments. The Windows 10.0.6 and 10.0.8 builds share the same AGPL-licensed merge implementation. Zotero may consolidate attachments by PDF bytes or by text similarity, so the plugin also requires the recorded PDF hashes, ownership marker, and tablet baseline before moving a connection. Undo can reverse a recorded repair after Zotero restores its original items. Ambiguous merges and two-link collisions hold the affected connection, and a queued deletion checks the native relations again before acting. The plugin stores only the verified link changes and keeps the native merge, Undo, and attachment handling in Zotero. [Zotero merge implementation](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/mergeItems.mjs)

The PDF reader compares an unlinked attachment with the saved original digests of linked PDFs. It uses Gecko's built-in Web Crypto on the local file, so the comparison can run during sync on the supported Windows Zotero 10.0.x series without a dependency. A unique match offers the linked PDF at the same page. Library Issues reuses the worker's existing PDF digest index and includes exact matches for already-filed references. Zotero's native duplicate and merge tools remain responsible for combining citation records. No link moves based on a filename, title, or approximate text match. [Zotero duplicate detection](https://www.zotero.org/support/duplicate_detection)

Confirmed folder and paper decisions use a separate, restart-safe profile queue. Each decision waits for the current worker operation, then checks the reviewed connection and case before applying. Zotero folder previews read actual collection memberships, items, and child records. The Zotero transaction verifies the preview again before using native item Trash and collection membership operations. We reuse Zotero’s maintained AGPL-3.0-or-later collection and item APIs on the supported Windows Zotero 10.0.x series. Native collection deletion alone offers all-items or collections-only behavior, so a small transaction combines the native operations for individual choices. No new dependency or reMarkable device API is required. [Zotero collection implementation](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/data/collection.js) · [Zotero item implementation](https://github.com/zotero/zotero/blob/main/chrome/content/zotero/xpcom/data/item.js)

Zotero owns the workspace and local files. The Windows helper remains the single writer for bridge state and paired operations. The page editor opens with Zotero’s current paper tags and the last committed page map when available. It saves the selected changes in the Zotero profile before reporting them as saved. The worker then applies the additions and removals to current tags and checks the connection, attachment, PDF digest, and stable page ID. Zotero item writes use the existing version check. Tag edits that need attention remain in the queue. Ordinary worker actions clicked during sync wait in the open session and are rechecked when applicable. Existing filing approvals retain their separate, restart-safe queue and review checks.

OneDrive documents its change notifications and ordered processing of changes. Microsoft Graph separately documents delta checkpoints, stable IDs, deletion records, and version-conditional uploads. reMarkable documents offline work and syncing on reconnection. Its public help describes device behavior. Dropbox’s engineering write-up describes why ordering and simultaneous device changes need explicit test coverage. [OneDrive sync](https://learn.microsoft.com/en-us/sharepoint/sync-process) · [Graph delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta) · [Graph conditional uploads](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession) · [reMarkable offline and sync](https://support.remarkable.com/s/article/Pair-your-reMarkable-with-the-cloud) · [Dropbox sync engineering](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)

We reused the existing Zotero profile queue pattern, Gecko `IOUtils` atomic replacement, the Python worker’s public-domain SQLite ledger, and the current reMarkable adapter. Mozilla maintains `IOUtils` in Gecko under the MPL. Both primitives are already part of the Windows build for Zotero 10.0.6 and later in the 10.0 series, so this change adds no runtime or device dependency. CloudKit’s pending-change API illustrates the pattern, but it targets Apple platforms and a CloudKit backend. Firestore’s offline cache targets its own backend and uses last-write-wins for changes to the same document. Neither fits the existing Zotero and reMarkable stores. The plugin needs only a small edit queue and scoped tag reconciliation.
