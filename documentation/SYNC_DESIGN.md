# Working while sync runs

Zotero owns the workspace and local files. The Windows helper remains the single writer for bridge state and paired operations. The page editor opens with Zotero’s current paper tags and the last committed page map when available. It saves the selected changes in the Zotero profile before reporting them as saved. The worker then applies the additions and removals to current tags and checks the connection, attachment, PDF digest, and stable page ID. Zotero item writes use the existing version check. Tag edits that need attention remain in the queue. Ordinary worker actions clicked during sync wait in the open session and are rechecked when applicable. Existing filing approvals retain their separate, restart-safe queue and review checks.

OneDrive documents its change notifications and ordered processing of changes. Microsoft Graph separately documents delta checkpoints, stable IDs, deletion records, and version-conditional uploads. reMarkable documents offline work and syncing on reconnection. Its public help describes device behavior. Dropbox’s engineering write-up describes why ordering and simultaneous device changes need explicit test coverage. [OneDrive sync](https://learn.microsoft.com/en-us/sharepoint/sync-process) · [Graph delta](https://learn.microsoft.com/en-us/graph/api/driveitem-delta) · [Graph conditional uploads](https://learn.microsoft.com/en-us/graph/api/driveitem-createuploadsession) · [reMarkable offline and sync](https://support.remarkable.com/s/article/Pair-your-reMarkable-with-the-cloud) · [Dropbox sync engineering](https://dropbox.tech/infrastructure/rewriting-the-heart-of-our-sync-engine)

We reused the existing Zotero profile queue pattern, Gecko `IOUtils` atomic replacement, the Python worker’s public-domain SQLite ledger, and the current reMarkable adapter. Mozilla maintains `IOUtils` in Gecko under the MPL. Both primitives are already part of the Windows build for Zotero 10.0.6 and later in the 10.0 series, so this change adds no runtime or device dependency. CloudKit’s pending-change API illustrates the pattern, but it targets Apple platforms and a CloudKit backend. Firestore’s offline cache targets its own backend and uses last-write-wins for changes to the same document. Neither fits the existing Zotero and reMarkable stores. The plugin needs only a small edit queue and scoped tag reconciliation.
